# 读写锁缺陷修复与回归测试

纯 Python 3 标准库实现，无第三方依赖。

## 文件

- `rwlock_buggy.py` — 修复前的缺陷实现（仅作复现对照）
- `rwlock_fixed.py` — 修复后的实现（写者优先）
- `test_rwlock.py` — 缺陷复现用例 + 修复回归测试

## 运行

```bash
python3 -m unittest test_rwlock -v
```

## 缺陷分析

### 缺陷 1：写者饥饿

修复前 `acquire_read` 只检查"是否有活动写者"，不关心是否有写者
正在等待。只要读请求接续到达，读者计数 `_readers` 永远回不到 0，
写者在 `_readers > 0` 上被无限期推迟。

复现（`test_writer_starvation`）：主线程持读锁，写者线程进入等待
（由观测钩子确定性确认），随后主线程做"读者接力"——每轮先加新
读者再释放旧读者，计数恒 >= 1，写者必然拿不到锁。全程用事件编排，
不靠 sleep 碰运气。

### 缺陷 2：双写者窗口

修复前 `acquire_write` 在监视器锁**内**完成条件检查，却在锁**外**
置位 `_writer_active`；`release_write` 也在锁外清除标志。两个写者
可以先后通过检查（都看到 `_writer_active == False`），再先后置位，
同时认为自己持有写锁。

复现（`test_double_writer_window`）：用 `threading.Barrier(2)` 替换
观测钩子，把两个写者精确钉在"检查已通过、标志未置位"的窗口里，
再同时放行，必然观察到临界区内同时有两个写者。

## 修复前后的加锁协议差异

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 读者进入条件 | 仅"无活动写者" | "无活动写者" **且** "无等待写者"（写者优先） |
| 写者检查与置位 | 检查在锁内、置位在锁外，存在窗口 | 检查与置位在**同一次持锁内**原子完成 |
| 写者释放 | 锁外清标志，再进锁 notify | 锁内清标志并 `notify_all` |
| 等待写者计数 | 无 | `_writers_waiting`，读者据此让路 |

修复后不变式（都在同一把 `Condition` 锁保护下维护）：

- 读者可进入 ⟺ `not _writer_active and _writers_waiting == 0`
- 写者可进入 ⟺ `not _writer_active and _readers == 0`
- `_writer_active` 的任何读写都发生在持锁期间

由此直接得到：写者一旦排队，新读者被挡住，存量读者有限时间内
释放完毕，写者必然进入（不会无限期饿死）；无写者等待时读者互不
阻塞，读并发不受影响。

## 为什么不会引入死锁

1. **单锁**：全部状态由同一把 `Condition` 互斥锁保护，不存在多锁
   嵌套，因而不可能形成锁序环（循环等待）。
2. **等待即让锁**：`cond.wait()` 语义上原子地释放互斥锁并挂起，
   等待者不占用任何资源，不满足"占有且等待"。
3. **唤醒必有来源**：每个等待条件（`_readers == 0`、
   `_writer_active == False`）的唯一变更点都在 `release_read` /
   `release_write` 中，且变更后必 `notify_all`；持锁者只依赖其他
   线程调用 release，而 release 不阻塞、不可被等待者阻止。
4. **前进性**：写者优先只改变唤醒顺序，不增加任何等待依赖；
   任意时刻至少有一个线程可前进（读者集合有限、写者队列有限）。

注意：本实现是写者优先。若写者流持续不断，理论上读者可能被推迟；
如需读写双向公平，可在此框架上改为 FIFO 队列（按到达顺序发放
许可），协议骨架与死锁论证不变。
